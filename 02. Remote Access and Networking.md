# 02. Remote Access and Networking

## 1. SSH and PuTTY

SSH gives a secure command-line session over the network. Most real servers have no monitor or keyboard, so administrators connect over SSH. The Windows laptop is the SSH client (PuTTY) and the VM runs the SSH server.

```
Windows 11 (PuTTY)  --SSH, TCP 22-->  Ubuntu Server (sshd)
```

**Confirm OpenSSH is running** from the VMware console:

```bash
sudo systemctl status ssh
```

If it is missing or stopped:

```bash
sudo apt install openssh-server
sudo systemctl start ssh
sudo systemctl enable ssh
```

**Find the server’s IP address:**

```bash
ip a
```

The address matters because everything depends on it: PuTTY, WinSCP, the browser and, later, SNMP. I noted it down.

**Connect with PuTTY:** enter the server’s IP, port 22 and connection type SSH, then **Open**. On the first connection PuTTY shows a host-key warning. The key identifies the server and protects against impersonation. The warning can be legitimate, for example after a rebuild, but could also signal a problem. Because this was my own VM, I accepted it and logged in with my Ubuntu account.

I increased the PuTTY font to 16 (title bar, Change Settings, Window, Appearance) for comfort during long sessions.

## 2. Networking fundamentals

| Command | Shows |
| --- | --- |
| `ip a` | Interfaces, addresses, prefix and operational status |
| `ip route` | The routing table; the default route points at the home router `192.168.1.1` |

The default route means: if there is no more specific route, send the traffic to this gateway.

## 3. Static IP with Netplan

The VM received its address by DHCP, which could change after a reboot or lease renewal. A server needs a predictable address, so I configured a static one. Ubuntu Server uses **Netplan**, which reads YAML files.

```bash
sudo nano /etc/netplan/50-cloud-init.yaml
```

The file name can vary, so I checked it rather than assuming. Configuration (also in `configs/50-cloud-init.yaml.netplan`):

```yaml
network:
version:2
ethernets:
ens33:
dhcp4:no
addresses:[192.168.1.149/24]
routes:
-to: default
via:192.168.1.1
nameservers:
addresses:[1.1.1.1,8.8.8.8]
```

| Line | Meaning |
| --- | --- |
| `dhcp4: no` | Do not request an IPv4 address from DHCP |
| `addresses` | The static IP and prefix |
| `via: 192.168.1.1` | The default gateway |
| `nameservers` | DNS servers |

YAML is strict about indentation: spaces, never tabs, and alignment defines structure. A small mistake can make Netplan reject the file.

Apply it:

```bash
sudo netplan apply
```

Applying a new IP over SSH can drop the session, since it was using the old address. I kept the VMware console available as a backup way in. Never change the only connection to a remote machine without a second way in.

**Test each part separately:**

```bash
ping 8.8.8.8
ping google.com
```

The first proves the server can reach the outside network by IP, so the address, interface and gateway work. The second proves DNS resolution works. Both succeeded.
