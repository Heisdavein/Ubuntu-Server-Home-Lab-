# 07. Security Hardening

A server that works but is poorly secured is still a problem. Security is built in layers: even if one defence is bypassed, another slows or stops an attacker. Related files: `configs/`.

## 1. Firewall with UFW

A firewall decides which network traffic may reach the server. UFW (Uncomplicated Firewall) is Ubuntu’s front end.

```bash
sudo apt install ufw
sudo ufw status
sudo ufw allow OpenSSH
sudo ufw allow "Apache Full"
sudo ufw enable
sudo ufw status numbered
```

**Order matters.** SSH is allowed before the firewall is enabled. Enabling a firewall that blocks SSH over a remote session would cut off access, and on a production machine could mean travelling to the server. The same rules can be written by port: `allow 22/tcp`, `80/tcp`, `443/tcp`.

Rules I reviewed for managing the firewall, but did not apply:

```bash
sudo ufw allow from 192.168.1.150 to any port 21     # one specific computer
sudo ufw deny from 10.10.10.100                      # block an address
sudo ufw status numbered                             # list rules with numbers
sudo ufw delete 2                                    # remove a rule by number
```

Later, SNMP was allowed from the LAN only (see Monitoring).

## 2. SSH hardening

Settings live in `/etc/ssh/sshd_config` (see `configs/sshd_config-changes.txt`).

- **Port:** I reviewed changing the default port 22, for example to `10422`, which would then need `ssh -p 10422 user@server`. It reduces noise from automated scans but is not real security, so I did not change mine.
- **Root login:** `PermitRootLogin no`. Attackers try `root` first. Disabling it means they would also need to guess a valid username, and administrators use a named account plus `sudo`, which also leaves a clearer audit trail.

```bash
sudo systemctl restart ssh
sudo systemctl status ssh
```

Verifying the service right after a change catches configuration mistakes before they grow.

## 3. SSH key authentication

A key pair has a **private key**, which stays on my Windows machine, and a **public key** placed on the server. The server proves who I am through the key instead of a password that can be guessed.

```bash
ssh-keygen                           # on the Windows machine
ssh-copy-id klint@192.168.1.149      # copy the public key to the server
ssh klint@192.168.1.149              # test
```

The test login authenticated with the private key and asked for no password.

Only after that did I disable passwords in `sshd_config`:

```
PasswordAuthentication no
PubkeyAuthentication yes
```

```bash
sudo systemctl restart ssh
```

**Safety checks.** I tested the key first, kept a working session open while testing a new one, and kept the VMware console as a recovery route. These guard against locking myself out.

## 4. Fail2Ban

Brute-force attackers scan for SSH servers and try common usernames and many passwords. Fail2Ban watches the authentication logs and blocks addresses with repeated failures.

```bash
sudo apt install fail2ban -y
sudo systemctl status fail2ban
sudo systemctl enable fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
```

I created a local override instead of editing the package’s file, so my settings survive upgrades:

```bash
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
sudo nano /etc/fail2ban/jail.local
```

In the `[sshd]` section (`configs/jail.local-sshd.txt`):

| Setting | Value | Meaning |
| --- | --- | --- |
| `maxretry` | 5 | Failures allowed before action |
| `findtime` | 600 | Window in seconds (10 minutes) |
| `bantime` | 36000 | Ban duration in seconds (about 10 hours) |

So an address that fails five times within ten minutes is blocked for roughly ten hours, while a user who mistypes once or twice is unaffected. After editing, `sudo systemctl restart fail2ban` reloads the configuration, and `sudo fail2ban-client status sshd` shows the jail.

## 5. Advanced hardening

| Area | What I did |
| --- | --- |
| Automatic security updates | `sudo apt install unattended-upgrades -y`, then `sudo dpkg-reconfigure --priority=low unattended-upgrades` |
| AppArmor | Checked with `sudo aa-status`; installed `apparmor-profiles` and `apparmor-utils`. AppArmor confines each application to the resources it needs |
| Service audit | `sudo ss -tuln` for listening services, `systemctl list-unit-files --type=service \| grep enabled` for services that start at boot; unneeded ones can be disabled with `sudo systemctl disable` |
| Users and groups | Reviewed for unused accounts (`getent group`, `sudo deluser`, `sudo delgroup`) |
| Sensitive file permissions | `chmod 600 ~/.ssh/authorized_keys`, `chmod 644 /etc/ssh/sshd_config`, `chmod 700` on private scripts |
| Two-factor authentication | Installed `libpam-google-authenticator` and ran `google-authenticator`. SSH and PAM were not configured to require it, so it was treated as optional for a lab not exposed to the internet |

Fewer running services mean a smaller attack surface, and unattended updates mean fixes are not forgotten.

## Layers in place

| Layer | Control |
| --- | --- |
| Network | UFW allows only required traffic |
| Authentication | Key login, passwords disabled, root login disabled |
| Response | Fail2Ban blocks repeated failures |
| Software | Automatic security updates, AppArmor |
| Attack surface | Listening ports and enabled services audited |
| Data | Strict permissions on sensitive files |
